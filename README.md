# Modern Data Stack Pipeline — SYNTHETIC DATA

**Business question:** A streaming order feed delivers duplicates, late
events, and malformed rows. How do you turn it into trustworthy daily
revenue numbers with an orchestrated, tested pipeline?

**Why this project:** Data Engineer postings in late October 2026 keep
asking for exactly this stack — Airflow orchestration, dbt-style modelling
and tests, and a cloud warehouse (Snowflake) — and several postings flag
that stack as the gap (e.g. Lyra Health, Banc of California, EDO, and a
StepStone role built on Snowflake/dbt/Airflow). This project demonstrates
the transferable core of that stack end to end. It is a portfolio skill
demo built from synthetic data. It is **not** work experience and the
numbers below are **not** real company results.

**Honest labelling of the stack:** this runs locally, not on the cloud
services. SQLite stands in for Snowflake as the warehouse, the models are
plain SQL written in dbt style (staging → intermediate → marts, plus
schema-style tests), and the DAG is an Airflow-style task graph executed
by a small Python runner. No dbt Cloud, Snowflake, or Airflow server is
involved, and nothing here should be read as production experience with
those services — the SQL uses no SQLite-only features except `DATE()`,
so the models port directly to dbt + Snowflake, and the DAG definition
maps directly onto an Airflow DAG.

## Architecture

```
raw_events.jsonl  (Kafka-style event stream, received_at order)
      │  ingest
      ▼
bronze_events     (raw, as received — nothing dropped)
      │  stg_events.sql
      ▼
stg_events        (typed staging)
      │  int_events_deduped.sql
      ├─► quarantine_events   (bad rows + reason, auditable)
      ▼
int_events_deduped (one row per event_id, latest delivery wins)
      │  marts.sql
      ├─► dim_customers
      ├─► fct_orders          (latest event per order wins — a late
      │                         correction overwrites earlier state)
      └─► mart_daily_revenue, mart_revenue_by_category,
          mart_orders_by_channel
```

Orchestration: `dags/daily_pipeline.py` declares the task graph
(ingest → build_staging → build_intermediate → build_marts → run_tests →
publish); `src/run_pipeline.py` executes it in topological order, retries
each task once on failure, and stops downstream tasks if one fails.
Re-running is idempotent — every model table is dropped and rebuilt.

## Data

`data/raw_events.jsonl` — 6,230 synthetic order events, Jan–Jun 2026,
generated by `src/generate_events.py` (seed 20261102, so a re-run
reproduces the file exactly). Deliberate defects, mirroring a real
stream: 150 duplicate deliveries, 56 late-arriving events (received more
than 2 days after the event), and 80 malformed rows (20 each: null
amount, negative amount, unknown status, missing order_id).

## Data tests (all pass — see `results/dag_run.json`)

Unique event_id in silver, unique order_id in fct_orders, no null or
negative amounts in fct_orders, bronze reconciliation
(6,230 = 6,000 silver + 150 duplicates removed + 80 quarantined),
mart revenue reconciles to fct_orders paid total, no null mart dates.

Run it:

```bash
python3 src/generate_events.py
python3 src/run_pipeline.py
```

A from-scratch re-run (warehouse and results deleted) reproduces the
mart CSVs byte-for-byte.

## Interview talking points

- Bronze/silver/gold is a discipline, not a folder layout: bronze never
  drops anything, so every downstream number can be traced back to a
  received event, and quarantined rows carry a reason.
- Dedupe key choice matters: dedupe on `event_id` (delivery identity),
  then resolve order state separately by latest `event_time` — conflating
  the two is how late corrections get lost.
- Tests are part of the pipeline, not an afterthought: the publish step
  never runs if a test fails, and the reconciliation check (bronze =
  silver + duplicates + quarantine) catches silent row loss.
- Idempotent rebuilds make re-runs safe: re-running the DAG after a
  failure does not double-count anything.
